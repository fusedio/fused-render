App page version dropdown

The app page gets a version dropdown that puts the whole page — Overview, Files and API — on a past commit, and the Git tab is deleted.

The snapshot machinery already exists from the preceding work on this branch: GET /api/git/snapshot extracts an app folder at a sha, and _snapshot is URL state that resolves to an extracted tree. This applies both to the app page. What is missing is a way to choose a commit outside the git sidebar — hence a commits route and a dropdown — and the Git tab, which was the app page's only git surface, goes away rather than sitting beside a second one.

Owner's calls, both settled: the app page becomes read-only about git (staging, committing, branches and push/pull leave the app page entirely — they remain in the explorer's folder view, where the git template still lives), and picking a version affects the whole page, not just the Overview frame.

Amendment — version numbers, not shas (owner, after approval)

The app page is for basic users, so the picker reads v1, v2, v3 — the commit's ordinal among commits touching this app folder — rather than a short sha. v1 is the oldest such commit; the newest is v<total>.

The label is presentation; the sha stays the identity. _snapshot in the URL remains a hex sha, never a version number — a v-number counts commits reachable from HEAD touching that folder, so it renumbers on a rebase or a branch switch, and a shared link keyed on it would silently come to mean a different commit. Keep the short sha available as the row's title for anyone who wants it, but it is not the label.

This is a cosmetic change, and should stay one. The numbering is client-side index arithmetic over the list the picker already has. The only server-side part is one integer: the route reports the TOTAL number of commits touching the app folder (one git rev-list --count beside the log it already runs), so that a capped list still numbers its newest row correctly — without it, v7 silently becomes v5 when the row limit changes. Do not add a per-commit version field, a second round trip, or any numbering state.

Key decisions & risks

The commits route lives in git_snapshot.py, not a new module.
It needs the same repo-root resolution, app-folder scoping, mount refusal, posix_spawn-safe kwargs and refusal shapes. A separate module means a third copy of that discipline, and the parity is not test-enforced.
A deliberately smaller log than templates/git/log.py.
That reader answers diffs, pagination, rename detection and working-tree state. A dropdown needs a label per commit. Two implementations of "git log" now exist; the mitigation is that this one is small enough to read at a glance, and it is scoped to a single question.
No second carry rule for the app page.
appPageUrl(dir, tab, location.search) already preserves the query across tab hops, so _snapshot travels for free. The explorer's carries() rule exists because navigate() deliberately drops the query; that problem does not exist here.
Execution stays enabled under a snapshot.
The API tab's Execute runs the commit's own .py against the extracted tree. Refusing would be inconsistent with Overview, which runs the whole app at that commit — the point of the feature.
Rewrite against the page's own resolution, never the singleton.
Two apps in one repo share shas and several views mount at once; the explorer already shipped this defect once (round 2, finding 1). rewritePathAgainst(snap, path) exists precisely so a caller with its own validated resolution uses it.
Risk: the app page loses git write actions with no in-page pointer.
Owner's call — "preview only", no link kept. Someone who used the Git tab to commit must now open the folder in the explorer. Worth watching for as feedback rather than pre-emptively softening.
Risk: AppPage.tsx has no render-test precedent.
The explorer's Preview.tsx wiring for the same mechanism shipped reviewed-but-not-test-verified for this reason. Tasks 2–4 add AppPage.test.tsx and AppVersionPicker.test.tsx; if a render test proves impractical here too, say so in the decisions log rather than quietly dropping the coverage.

How we'll know it works

Open an app that lives in a git repo from the sidebar. The header shows a version picker reading "Live"; there is no Git tab. Pick a commit from before a change to one of the app's readers: Overview re-renders the app as it behaved then, Files lists that commit's tree, API lists that commit's endpoints, and switching between the three tabs keeps the selection. Pick "Live" and all three return to the working tree. Open an app that is not inside a git repo and no picker appears at all.
