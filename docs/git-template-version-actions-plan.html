Git template — prominent Preview, Checkout, Revert

Make previewing a commit a first-class, always-visible action, and add two write actions beside it: restore the app folder to a commit, and revert a commit.

Approach. The preview eye becomes a labelled button that is always drawn (not hover-revealed), keeping the existing capability gate that hides it where a preview could never land. Two new ops join ops.py behind the module's existing refusal machinery: app_restore (checkout the app folder at a sha, then commit it) and revert (git revert). Both refuse outright on a dirty working tree, so neither can ever collide with uncommitted work.

Nothing here rewrites history — revert adds a commit and app_restore adds a commit, so test_git_ops.py's "no history rewriting" posture is preserved as-is.

What each button does

ButtonWhereEffectScope
Preview changed Every commit row, always visible Unchanged behaviour — sets _snapshot=<sha> via the shell hop. Read-only. App folder
Checkout new The previewing banner, beside "Back to now" — only while previewing git checkout <sha> -- <app_dir> then git commit. HEAD stays on the branch; a new commit restores the app folder's contents. App folder only
Revert new Expanded (selected) commit pane git revert --no-edit <sha> — a new commit undoing that commit. Whole repo

Why the banner is the right home for Checkout. It solves the row-width problem that two labelled buttons created, but the better reason is sequencing: Checkout is only offered for a version you are already looking at, so "preview, then adopt" is the only path to it. There is no way to commit a rollback to a version you never saw, and the banner already names that version — the button needs no label of its own to say which commit it means.

Guard chain

Every new guard fails into the module's existing _Refused path — the same shape _refuse_mounts already uses, so the view renders it with no new error handling.

Key decisions & risks

"Always shown" keeps the canPreview gate
The gate has two halves — a content pane to drive, and an enclosing app folder — and D701 added the second because without it the eye promised a preview that 404s and silently does nothing. Drawing the button everywhere would reintroduce exactly that. So the change is hover-revealed → drawn at rest, not conditional → unconditional. Flagging it because it is a narrower reading of "always" than the words alone.
The latest-commit dot goes; the previewing pill's dot stays
Two dots shared one colour and one stated meaning ("the commit the files belong to"), but only one of them was ever informative. The latest-commit dot appears only when nothing is previewed, where it marks the top row of a newest-first list; the previewing pill's dot appears exactly when the answer is not obvious. Removing the first is what lets the second keep the colour unambiguously.
Checkout lives in the previewing banner, not on the rows
Your call, and it turned out to carry a design benefit past the width problem it solved: Checkout can only be reached through a preview, so nothing can commit a rollback to a version that was never looked at. It also means the button needs no per-commit label — the banner already names the version it means.
Checkout commits rather than leaving working-tree changes
Per your amendment. It also composes: a committed restore is itself revertible by the new Revert button, where an uncommitted one would need a different undo.
The dirty-tree guard is repo-wide, not app-scoped
Revert is repo-wide so it needs a repo-wide check regardless. Applying the same rule to Checkout costs a little strictness — an edit in an unrelated folder blocks it — but one rule the user can predict beats two that differ by which button they pressed. Narrowing Checkout's guard to the app folder later is a small change if the strictness bites.
Both ops are DESTRUCTIVE_OPS
Neither can lose work once the dirty guard holds, so this is about consent, not recovery: both write to history on one click, and that deserves the confirmation step. The classification is also what the view keys its confirm UI off, so it is the mechanism as well as the label.
Risk — a conflicting revert leaving the repo mid-operation
The worst outcome here: a user left in a conflicted state by a sidebar button, with no UI to finish it. Task 3 aborts and refuses instead, and asserts the absence of REVERT_HEAD so a regression is caught rather than discovered.
Risk — app_restore reaching outside the app folder
A pathspec bug would make this a repo-wide rollback wearing an app-scoped label. The outside-the-folder byte-identity assertion in task 2 is the specific guard, and it is called out as non-skippable for that reason.
ops.py cannot import fused_render
Templates are packaged data (SPEC PY-15 / D166), so the app-folder walk goes through shared/app_entry.py via the sys.path hop log.py and condition.py already use — not through app_listing.enclosing_app_dir, which is the server-side twin of the same rule.

How we'll know it works

In a repo app: every commit row shows a Preview button without hovering, and still shows its relative time. Previewing swaps the pane to that commit read-only and raises the banner, which now offers Checkout beside "Back to now". Checkout, after confirming, leaves HEAD on the branch with one new commit whose app folder matches the previewed version and whose other folders are byte-identical, then drops back to "now". Expanding a commit shows Revert, which adds an undo commit. With any uncommitted change in the repo, Checkout and Revert both refuse with a readable message and change nothing.
