Bot Browser Hand-off

Overnight research, 2026-10-08. Why the bots' Chrome control is flaky, what everyone else does, four approaches prototyped against one harness, and one pick.

Verdict: launch each profile's Chrome once, headed, and never relaunch it

This is not the windows path that already failed. That path popped a window by killing headless Chrome and relaunching the profile visible, then killed it again to hand back: two process boundaries per hand-off. A launches each profile's Chrome once and never relaunches it. The window the human sees is the same; the process boundary is gone.

Pick A. One headed Chrome per profile, kept alive for the life of the server. A bot's window is parked off-screen when hidden (macOS leaves a 40-point corner on screen) and its tab stays live through Emulation.setFocusEmulationEnabled. Take-over is one CDP call that moves the window on screen and focuses it; hand-back is one call that parks it again. Minimizing is not the hidden state: a minimized window hangs captureScreenshot after any navigation, which three of the four prototype agents hit independently. The human drives a real Chrome window: real keyboard, IME, clipboard, password manager, passkeys, file pickers. The bot resumes on the same tab, same target id, same process.

Keep B's work. The in-app live view stays as the monitor, with the corrected key forwarder, and can remain an optional interactive path. Its input bug is a one-line class of error (windowsVirtualKeyCode = ord(key)), proven and fixed in the prototype.

Why A over B, since both passed every harness test: the tie-breaker is human-side fidelity. A's cost is desktop footprint (a Chrome in the Dock and Cmd-Tab, a visible window corner, a watchdog for users who minimize it); B's cost is a permanent input ceiling. Footprint is a wart; the ceiling is the class of bug this report was commissioned over. The in-app view can never give the human more than synthesized input, and the past year of "typing a dot does not work" chasing is exactly that ceiling. The window route gets fidelity from the OS for free. Playwright (D) and the extension (C) also pass, but each adds a layer without removing a failure mode.

Why it is flaky today

Every take-over and hand-back is a Chrome process boundary. BrowserProcess.set_visible in fused_render/bots/browser.py kills the headless Chrome and relaunches the same profile as a visible window, then does it again in reverse. Each flip means a new debugging port, new target ids, a profile unlock and re-seal, dead screencast and input sessions, and, on a shared profile, the visibility of every bot's window coupled to one bot's hand-off. PRs #1492 and #1494 patched that coupling; they could not remove it.

The Chromium source names the mechanisms that bite on each relaunch:

  • ProcessSingleton forwarding. If the old Chrome pid is still alive when the new one starts, the new process hands its command line to the old one and exits. Its --headless, port and window flags are discarded. If the old one does not answer it waits up to 20 s, then kills it. Symptoms: "relaunched but no port appears", "window opened in the dying instance", 20 s hangs. process_singleton_posix.cc
  • Sticky exit_type = "Crashed". Chrome writes it on every start and clears it only on clean shutdown or a human acknowledging the restore bubble. A headless run never acknowledges, so every later visible launch shows "Restore pages?". exit_type_service.cc
  • Port race. Picking a free port, then passing it, is a time-of-check race. Puppeteer passes --remote-debugging-port=0 and reads DevToolsActivePort.
  • Everything is re-keyed. Target ids, session ids, execution contexts, screencast sessions and the per-session focus emulation all die with the process. The bot has to find "its" tab again.
  • Fingerprint drift. Headless and headed runs of one profile differ in UA, window size and GPU, so some sites treat the bot as a new device after the human logs in.

All five disappear if the process is never relaunched for a hand-off. The in-app live view never needed a relaunch; it failed on input fidelity alone.

The "." bug, proven

Both key forwarders compute the Windows virtual-key code as ord(key.upper()): keyParams in frontend/src/apps/bots/lib/live.ts:59 and _key_params in fused_render/bots/browser.py:152. That is right only for A–Z and 0–9. For "." it yields 46, which is VK_DELETE. Blink maps the virtual key to an editing command before it reads text, so the keystroke deletes the next character and types nothing. The bot's own type tool uses Input.insertText and was immune; the human in the live view and the bot's press tool were not.

Shifted characters collide too: ( is 40 = ArrowDown, % 37 = ArrowLeft, & 38 = ArrowUp, $ 36 = Home, # 35 = End, ! 33 = PageUp, " 34 = PageDown. Cmd+A over CDP does nothing on macOS unless commands: ["selectAll"] is sent, because CDP key events bypass Cocoa key bindings. Two more traps found while fixing it:

  • Sending nativeVirtualKeyCode on macOS flips the tab to visibilityState: hidden and silently stops the screencast. Never send it.
  • DevTools' own screencast forwards event.keyCode straight from the viewer browser, which already did the layout mapping. That is the simplest correct fix. Puppeteer's USKeyboardLayout table plus Playwright's macEditingCommands is the complete one; the prototype ports both and the Python and JS copies agree on 3776 key/modifier vectors.

Prior art: nobody relaunches, nobody auto-detects the human

Ten products in the table below, twelve looked at, primary sources fetched where they exist. Two families: cloud vendors run one headful Chrome and show the human a live view of it; local tools drive the user's real headed tab and the human just clicks in it. Four approaches, one harness

Each prototype is throwaway code in the session scratchpad, run against the same eight tests: T1 bot types a punctuation string byte-exact; T2 human takes over and types; T3 bot resumes on the same target id and pid; T4 twenty take-over/hand-back cycles; T5 two bots on one profile, one taken over; T6 user closes the tab; T7 screenshot and screencast while the bot's tab is hidden; T8 the orchestrator restarts and re-attaches to the running Chrome.

A · selected

Always-headed Chrome, never relaunch

One headed Chrome per profile, own --user-data-dir, port read from DevToolsActivePort. Bot windows parked off-screen (Browser.setWindowBounds left/top 99999, clamped by macOS) with focus emulation on each bot tab. Take-over: move on-screen + Target.activateTarget, 4 ms CDP, 160 ms with app activation. Hand-back: park again.

Human gets a real window; no automation bar. Costs: a 40-point window corner stays visible, Chrome shows in Dock, Cmd-Tab and Mission Control, the user can drag or minimize it (needs a watchdog), and a long-running Chrome will meet "relaunch to update".

B · keep as monitor

Headless + in-app live view, input fixed

Current architecture with the forwarder rewritten (Puppeteer table, mac commands, insertText fallback, hidden textarea for IME and paste). Take-over is a server-side driver flag; flip measured at 0.2 ms.

Zero desktop footprint. Ceiling: synthesized input only. No native IME, passkeys, password managers, file pickers, OS dialogs; some sites fingerprint headless.

C

MV3 extension over chrome.debugger

Headed Chrome loads a relay extension via CDP Extensions.loadUnpacked (branded Chrome 137+ ignores --load-extension). Python ↔ WebSocket ↔ service worker ↔ chrome.debugger. Take-over = detach + activate.

The loaded extension is ephemeral (never persisted), so it still needs the debugging port every launch: a layer on top, not a replacement. Cannot attach to chrome:// tabs; refuses data: navigations; minimized windows stay dead even with focus emulation under this session type. Only wins if the goal becomes "drive the user's everyday Chrome".

D

Playwright (Python) as the CDP client

Works only as connect_over_cdp to a Chrome we launch ourselves; launch_persistent_context dies with the Python process. Typing is byte-exact out of the box.

135 MB installed (116 MB bundled node), sync-vs-asyncio boundary, and it auto-dismisses JS dialogs when no listener is attached, so the human would lose alert/confirm/beforeunload during take-over. The hand-rolled WebSocket client was never the root cause.

  • Focus emulation is per CDP session. It dies on detach or reconnect and must be re-enabled for every bot tab. It also makes document.hasFocus() true, so visibility-gated analytics and autoplay behave as if the user is looking.
  • Only --enable-automation causes the infobar. Puppeteer and Playwright add it by default; we do not pass it. --disable-infobars is dead. Under the extension path, --silent-debugger-extension-api removes the "started debugging" bar, whose Cancel button would otherwise detach every bot at once.
  • Input.setIgnoreInputEvents blocks CDP input too, so it cannot lock the human out while the bot types. Nobody surveyed locks the human out; they gate the bot.
  • Chrome 136+ silently refuses remote debugging on the default profile directory in branded builds; Chrome 137+ ignores --load-extension; Chrome 144+ adds a user-toggled approval-mode debugging server for the everyday profile, with a consent dialog per connection.
  • Pipe vs port. --remote-debugging-pipe is private and race-free but Chrome dies with its parent, which breaks T8 and any server restart. Keep the port; take it from DevToolsActivePort after launch rather than choosing it first.

Plan for A inside fused_render/bots/browser.py

  1. Ship the one-line fixes first, independent of the rest: replace ord(key.upper()) in live.ts:59 with e.keyCode from the viewer's KeyboardEvent, and in browser.py:152 with the Puppeteer table; send mac commands for Cmd chords; never send nativeVirtualKeyCode.
  2. BrowserProcess.start launches headed once per profile with the browser-use flag set above plus --no-startup-window, --remote-debugging-port=0, and reads <profile>/DevToolsActivePort. The visible argument and the headless/visible relaunch in set_visible go away. stop keeps Browser.close → wait for pid and SingletonLock → SIGTERM → SIGKILL the process group, and is used only for idle sleep, seal, crash, or update.
  3. Each bot gets a window via Target.createTarget {newWindow: true, focus: false}, parked off-screen at once, with Emulation.setFocusEmulationEnabled(true) on the bot's page session and re-applied inside _connect on every reconnect. One window per bot keeps other bots out of the human's tab strip during a take-over; the park/unpark is per window, so #1492's "last bot hands back" coupling disappears.
  4. Take-over (Bot.window(True)): set meta.control, pause the bot, Browser.setWindowBounds to an on-screen position, Target.activateTarget, and activate the app (160 ms end to end). Every bot input call checks the control flag and refuses while the human drives (B's harness asserted this each cycle). Hand-back: park off-screen, re-enable focus emulation, clear the flag, bot re-observes before its next step. No product surveyed tries to reconcile what the human did; neither should we.
  5. Watchdog. If the user minimizes the window, hides Chrome with Cmd-H, or a monitor change undoes the clamp, document.visibilityState goes hidden and the next screenshot after a navigation hangs. Poll the window state or visibility on the bot's session and re-park the window. Also plan a scheduled restart path: Chrome self-updated from .39 to .40 during the overnight run, and an always-running Chrome will ask to relaunch.
  6. Window closed by the user (window_closed today relaunches): treat Target.targetDestroyed for the bot's tab as "hand back and open a fresh minimized window on the next step", same process.
  7. Live view keeps streaming the same target in the app as the monitor during bot and human phases, read-only by default, interactive behind the corrected forwarder as an option for users who prefer not to leave the app.
  8. Cmd-Q is the new failure mode. During a take-over the bots' Chrome has OS focus and appears in the Dock and Cmd-Tab as a second "Google Chrome" beside the user's own. One reflexive Cmd-Q quits every bot on that profile and forces the relaunch path this design retires. Set browser.confirm_to_quit (Chrome's "Warn Before Quitting") in each bot profile's Preferences, and treat a quit as a crash recovery, not a hand-back.
  9. Encryption at rest changes shape. Today the profile re-seals on every hand-off because Chrome stops. Under A it stays unsealed for Chrome's lifetime and seals on idle sleep, so encrypt means "sealed while asleep", not "sealed between actions".
  10. macOS only, so far. Chrome on macOS stays alive with zero windows; on Windows and Linux closing the last window exits Chrome, which breaks "user closed the tab, bot opens a fresh one in the same process". Verify --keep-alive-for-test or keep one hidden window there before enabling this on those platforms.
  11. Verify by hand on the first build: real keyboard into the restored window, IME, password manager autofill, Mac sleep/lock, whether the automation bar ever appears, and above all several parked bot windows in one process over hours. Window-per-bot is the recommended shape and that long-run case has the thinnest evidence (A's T5 only).

Harness hazards worth remembering

  • A cleanup helper that pgrep'd the shared scratchpad tag killed sibling prototypes' Chromes mid-run; it was changed to match only the caller's profile prefix. Any production cleanup must match --user-data-dir=<our profile>, never "Chrome".
  • A data: test page containing % or # is percent-decoded or truncated; one reconcile run reported a false negative because its animation never ran.
  • Chrome may open a stray chrome://settings/help tab on first launch of a fresh profile; always address tabs by target id, never by position.
  • Screenshot freshness must be checked by content, not by a quick return: a minimized window returns a stale cached frame in 30 ms and looks healthy.

Unverified

  • Many minimized bot windows in one process over hours; behaviour across Mac sleep and screen lock.
  • Operator's and Skyvern's internal hand-off mechanics; Browserbase's forwarder source.
  • Whether sites that fingerprint headless Chrome behave differently once bots run headed (expected improvement, not measured).
