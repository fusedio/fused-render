App-folder snapshot preview

A commit clicked in the git view puts the shell into a _snapshot=<sha> state, and every template under it — the file explorer included — reads the enclosing app folder as of that commit.

Today _rev re-srcs one frame and the runtime resolves that single file's bytes through /api/git/show, so a historical page renders against today's .py readers, assets and data — and nothing but that one frame knows a revision is in play. Instead: the server extracts the enclosing app folder at that sha into ~/.fused-render/app-versions/<key>/<sha>/, the shell carries _snapshot=<sha> as top-level URL state, and the runtime resolves any path inside the app folder against the extracted tree. Templates get it for free; ones that want to say so out loud read the param themselves. The single-file mechanism is then deleted.

Two things that already exist

A predecessor design extracted these trees and was deleted in D243 — but both guardrails were kept with no producer left: mount.py::_is_under_snapshot_root (mount.py:53-92) makes every /api/fs mutation 403 readonly under that prefix and makes _writable report false, so a framed editor draws read-only up front; and snapshot=1 / IS_SNAPSHOT (router.ts:104-150) is the shell's frozen-tree framing. This plan writes the missing producer and adds the sha-carrying param beside the existing flag.

git: retire the single-file _rev preview

Key decisions & risks

A top-level param, reversing preview-rev.ts's founding argument.
That module refuses to be a param because a _rev would leak onto the next file and into bookmarks. Owner's call, and the leak is what is wanted here: the state must reach the explorer and every template, which in-memory state structurally cannot. The two leaks are answered rather than ignored — the carry rule bounds it to the app folder, and a bookmark of an app at a commit is a coherent thing to have.
The runtime rewrites paths; it does not fetch bytes.
The deleted helpers routed each read through /api/git/show, which is why a .py reader could not be covered. Rewriting app_dir → extracted dir makes every read a plain filesystem read of a real file, so runPython is fixed by the same three lines as readFile.
Extraction rather than git cat-file behind a /rev/<sha>/ prefix.
The prefix keeps resolve-on-read and needs no disk, but cannot make a Python reader truthful without changing the main() contract (the deferral at runtime.js:2514). Owner's call: too much plumbing.
The extraction root is ~/.fused-render/app-versions/, not $TMPDIR.
That literal prefix is hardcoded in _is_under_snapshot_root (mount.py:90) and is what makes /api/fs mutations 403 and _writable false. Under $TMPDIR the frame looks live and editable while saves fail late or land in a tree the OS reaps mid-session.
Preview is app-only; no app above the target means no eye and no param.
Owner's call. A frozen listing of an arbitrary folder is what the deleted history mode was. The canPreview gate (template.html:1441,3428) already models "no pane to drive"; "no app folder" joins it.
The entry page is resolved inside the extracted tree.
An app whose entry was renamed since must open at the entry that commit had, not a filename that did not exist yet.
Risk: _snapshot must be stripped from page params.
Shell params reaching a page's own query is a known live defect — _side=claude blanks a page URL-syncing model=. _snapshot is forwarded onto frame srcs deliberately, so it must be in the shell's strip list on the way into page params, or a page with its own snapshot state collides with it.
Risk: the runtime edit in task 4 touches shared read helpers.
Those helpers serve every call, snapshot or not. The rewrite must be a no-op when the param is absent; the served-runtime pytest slice plus bun test are the check.
Risk: extraction latency on the first click.
A cache hit is a stat; a miss forks git archive and writes a tree. Scoped to one app subfolder rather than a repo snapshot, which is what makes it tolerable. If a large app feels slow, the answer is a spinner, not a smaller extraction.
Deferred: no preview control on the app page's Git tab.
Its Git tab (AppPage.tsx:175-186) frames the template with no adjacent content pane, so canPreview is false there and stays false. Driving the Overview frame from that tab is a separate change.

How we'll know it works

Open an app inside a git repo, open the git sidebar, click a commit from before a change to one of the app's .py readers. The URL gains _snapshot=<sha>, the app renders as it behaved then — old reader output, old assets, old data — and the editor is read-only up front. Browse into the app's subfolders: the explorer lists that commit's files, and opening any of them in any template shows that commit's bytes. Walk the breadcrumb out of the app and the param is gone, live content is back. Reload mid-snapshot and you are still in it. Nothing under ~/.fused-render/app-versions/ is ever writable through /api/fs.
